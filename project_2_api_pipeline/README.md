# Weather API to PostgreSQL ETL Pipeline

## Overview

This project is an **ETL (Extract, Transform, Load) pipeline** written in Python. It calls the free [Open-Meteo](https://open-meteo.com/) weather API, extracts the current weather conditions for a given location (Berlin by default), reshapes the JSON response into a clean table row with `pandas`, and stores it in a **PostgreSQL** table named `weather_data`.

Each run adds one timestamped observation. Run it regularly and the table becomes a history of weather measurements. Every step is logged to a file, and database credentials are kept outside the code in a `.env` file.

## Problem Statement

Weather APIs only return the **current** value: once the API is called, yesterday's temperature is gone. Teams that need historical data (for dashboards, forecasting models or comparisons with sales or energy data) have to collect and store it themselves.

APIs also return nested JSON, which is not directly usable for SQL queries or BI tools. This pipeline solves both problems by:

- calling the API automatically and handling network and HTTP errors,
- flattening the JSON into a tabular structure with proper data types,
- storing each observation in PostgreSQL with an insertion timestamp, so a time series builds up over repeated runs.

## Pipeline Flow

```
Open-Meteo API  ──►  Extract  ──►  Transform  ──►  Load  ──►  PostgreSQL (table: weather_data)
```

### 1. Extract
`extract_data()` sends an HTTP `GET` request to the API endpoint. If the response status is `200`, the JSON body is returned as a Python dictionary. Any other status code, or any network error, is logged with its traceback and raised so the pipeline stops instead of loading bad data.

The default endpoint requests the current weather for Berlin (latitude `52.52`, longitude `13.41`):

```
https://api.open-meteo.com/v1/forecast?latitude=52.52&longitude=13.41&current_weather=true
```

### 2. Transform
`transform_data()` reads the `current_weather` block of the response and builds a one-row DataFrame with these columns:

| Column | Source field |
|---|---|
| `temperature` | `current_weather.temperature` (°C) |
| `windspeed` | `current_weather.windspeed` (km/h) |
| `winddirection` | `current_weather.winddirection` (degrees) |
| `observation_time` | `current_weather.time`, converted to a datetime |
| `latitude` | `latitude` |
| `longitude` | `longitude` |

### 3. Load
`load_data()` adds an `inserted_at` column (the time of the load) and **appends** the row to the `weather_data` table with SQLAlchemy. Existing rows are never modified, which is what builds the history.

### Orchestration and logging
`run_pipeline()` runs the three steps in order. Each stage writes timestamped messages to `logs/api_pipeline.log`, including full tracebacks when an error occurs.

## Database Schema

Create the target table before the first run:

```sql
CREATE TABLE weather_data (
    id               SERIAL PRIMARY KEY,
    temperature      FLOAT,
    windspeed        FLOAT,
    winddirection    FLOAT,
    observation_time TIMESTAMP,
    latitude         FLOAT,
    longitude        FLOAT,
    inserted_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

The `id` column is generated by PostgreSQL. The pipeline fills in every other column.

> **Why create it manually?** If the table does not exist, pandas creates it automatically, but with inferred types and **without** the auto-incrementing `id` primary key. Creating it yourself gives you the intended schema.

## How to Run

### Prerequisites

- Python 3.9 or later
- A running PostgreSQL server and an existing database
- A PostgreSQL user with permission to insert rows into `weather_data`
- Internet access (to reach the Open-Meteo API)

### 1. Get the project

```bash
cd project_2_api_pipeline
```

### 2. Create and activate a virtual environment

```bash
python3 -m venv venv
```

Activate it:

```bash
# Linux / macOS
source venv/bin/activate

# Windows (PowerShell)
venv\Scripts\Activate.ps1
```

Your terminal prompt should now start with `(venv)`.

### 3. Install the dependencies

```bash
pip install -r requirements.txt
```

### 4. Configure the environment variables

Create the file `config/.env` with the following content, adapted to your setup:

```env
DB_USER=your_db_user
DB_PASSWORD=your_db_password
DB_HOST=localhost
DB_PORT=5432
DB_NAME=your_db_name
```

| Variable | Description |
|---|---|
| `DB_USER` / `DB_PASSWORD` | PostgreSQL credentials (special characters are URL-encoded automatically) |
| `DB_HOST` / `DB_PORT` | Database server address and port |
| `DB_NAME` | Name of the target database |

> **Security:** never commit `config/.env` to version control. Add it to your `.gitignore`.

### 5. Create the table

Run the `CREATE TABLE` statement from the [Database Schema](#database-schema) section in your database (with `psql` or any SQL client).

### 6. Run the pipeline

From the project root:

```bash
python scripts/api_pipeline.py
```

To change the location, edit the `latitude` and `longitude` values in the `api_url` variable at the bottom of `scripts/api_pipeline.py`.

### 7. Check the results

- **Log file:** `cat logs/api_pipeline.log`
- **Database:**

```sql
SELECT * FROM weather_data ORDER BY inserted_at DESC LIMIT 5;
```

### 8. Deactivate the virtual environment (when finished)

```bash
deactivate
```

## Notes and Limitations

- **Each run adds a row.** The load step appends data, so the table grows with every execution. This is intended (it builds the history), but running the script twice within the same observation window can store the same observation twice. Deduplicate on `observation_time`, latitude and longitude if needed.
- **Fixed location.** The coordinates are hard-coded in the script. Moving them to the `.env` file would make the pipeline configurable without editing code.
- **One observation per run.** The pipeline stores a single current reading, not a forecast or a full history from the API.
- **No request timeout.** The API call has no timeout, so a network that hangs can block the script. Adding `timeout=...` to `requests.get` avoids this.
- **API terms.** Open-Meteo is free for non-commercial use and has fair-use limits; check their terms before running the pipeline at a high frequency or in a commercial setting.

## Key Learnings

This project demonstrates the following skills and concepts:

- **Consuming REST APIs:** sending HTTP requests with `requests` and handling status codes and network failures.
- **Working with JSON:** flattening a nested API response into a tabular structure with pandas.
- **ETL design:** separating extraction, transformation and loading into small, testable functions.
- **Data typing:** converting timestamps with `pd.to_datetime` and adding an audit column (`inserted_at`).
- **Database integration:** loading data into PostgreSQL with SQLAlchemy and designing a table with a generated primary key.
- **Error handling and logging:** catching specific exceptions, logging tracebacks with `logger.exception`, and re-raising so failures are never silent.
- **Configuration management:** keeping credentials out of the code with environment variables and `python-dotenv`.
- **Project hygiene:** a clear folder structure, a virtual environment, a `requirements.txt` for reproducibility, and documented code.

## Possible Improvements

- Read the coordinates and API URL from the `.env` file.
- Add a request timeout and retries with exponential backoff.
- Deduplicate observations before loading (or add a unique constraint with an upsert).
- Add unit tests for `transform_data()` using a sample API response.
- Schedule the pipeline with `cron` or Airflow (for example every 30 minutes) to build the time series automatically.
- Containerize the project with Docker.
